This is feedback for the question **“Which gaps do you still see with our PRs against master?”** It supplements the [earlier comparison](openlineage-gap-comparison-2026-09-28.md), whose five-item PR summary omits several core OpenLineage 1.53 behaviors. ## Reproduction convention

Use a disposable GMS built from the pinned head, with the default OpenLineage REST configuration and authorized token. POST JSON to `$GMS/openapi/openlineage/api/v1/lineage`; wait for the first event’s native aspect to be readable before sending the second. Read latest aspects at `$GMS/openapi/v3/entity/{entityType}/{encodedURN}?aspects=...&systemMetadata=true`. Preserve the complete request, response and aspect readbacks. Use the known Spark producer `https://github.com/OpenLineage/OpenLineage/tree/1.53.0/integration/spark` (or configure the orchestrator) so producer inference does not stop the probe before its intended path. [Shared endpoint/readback commands](openlineage-gap-comparison-2026-09-28.md); [stack endpoint dispatch](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-service/openapi-servlet/src/main/java/io/datahubproject/openapi/openlineage/controller/LineageApiImpl.java#L171).

For minimal sequence descriptions below, keep the same `run.runId`, `job.namespace`, `job.name`, `producer`, and `schemaURL` in both RunEvents, and change `eventTime` monotonically. The `eventTime` values are UTC RFC3339 strings; use distinct UUID run IDs between independent scenarios. The following valid core envelope can be used for run scenarios; change only the paths specified per probe:

```json
{
  "eventTime": "2026-09-29T10:00:00Z",
  "producer": "https://github.com/OpenLineage/OpenLineage/tree/1.53.0/integration/spark",
  "schemaURL": "https://openlineage.io/spec/2-0-2/OpenLineage.json#/$defs/RunEvent",
  "eventType": "START",
  "run": { "runId": "11111111-1111-4111-8111-111111111111" },
  "job": { "namespace": "specdemo", "name": "specdemo.task", "facets": {} },
  "inputs": [],
  "outputs": []
}
```

Each dataset in `inputs` or `outputs` below is an object such as `{"namespace":"postgres://warehouse:5432","name":"demo.a"}`. For a `JobEvent`/`DatasetEvent`, use the same base envelope, omit `eventType` and `run`, change `schemaURL` to the appropriate `#/$defs/JobEvent` or `#/$defs/DatasetEvent`, and provide its required top-level `job` or `dataset`. See the [pinned core event definitions](https://github.com/manuschillerdev/datahub/blob/feat/openlineage-conformance-combined/metadata-service/openapi-servlet/src/main/resources/openlineage/schemas/1.53.0/OpenLineage.json).

The base event, job tag/ownership variants, initial schema and schema tombstone, and explicit Job/Dataset lineage examples were validated offline with `jsonschema` against both the pinned core-event definition and the attached standard facet definition. This checks payload shape only; it does not establish endpoint acceptance or storage results.

### 1. Accumulative RunEvents lose prior I/O

**Contract.** OpenLineage 1.53 says runs are accumulative unless their emission pattern says otherwise; individual events can contain only partial information, and consumers combine the events for one run. [Run cycle](https://openlineage.io/docs/spec/run-cycle/) and [JobType emission mode](https://openlineage.io/docs/spec/facets/job-facets/job-type/).

**Minimal sequence.** Send the base `START` event with `inputs:[demo.a]`, `outputs:[]`. Send a `COMPLETE` event for the same run at `10:01Z` with `inputs:[]`, `outputs:[demo.b]`. Read the `dataProcessInstanceInput` and `dataProcessInstanceOutput` aspects at `urn:li:dataProcessInstance:11111111-1111-4111-8111-111111111111`, plus the DataJob graph aspect. The expected complete run reports input `demo.a` and output `demo.b`. The source predicts the final run input is **empty** and output is `demo.b`: on every event the converter builds arrays from that event alone, then emits unconditional **UPSERT** process-instance input/output aspects. The DataJob graph PATCH may still contain `demo.a`, masking the loss when only the job view is checked. [#19800 event-to-dataset mapping](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/converter/OpenLineageToDataHub.java#L1478); [run aspect writes](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/dataset/DatahubJob.java#L315); [master had the same overwrite path](https://github.com/datahub-project/datahub/blob/597a64dbd0b227b5e6dd0ad4d083a2d205e1fec1/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/dataset/DatahubJob.java#L285).

**Related snapshot gap.** Put a valid `job.facets.jobType` on two `RUNNING` events with `emissionPattern:{"eventTrigger":"PERIODIC","eventContentMode":"COMPLETE_SNAPSHOT","windowDuration":300}`, with standard facet headers and `processingType:"STREAMING",integration:"SPARK"`. First event carries `demo.a → demo.b`; second carries `demo.c → demo.d`. [The 1.53 mode](https://openlineage.io/docs/spec/facets/job-facets/job-type/) says each event is a self-contained window. The converter’s [`jobTypeProperties`](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/converter/OpenLineageToDataHub.java#L2332) does not read `emissionPattern`; default [`usePatch=true`](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/config/DatahubOpenlineageConfig.java#L65) [adds graph edges](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/dataset/DatahubJob.java#L267). The latest DataJob graph therefore contains both windows. That may be an intentional historical-union policy for the job entity; it is **not a representation of the current window**, and the mapping must say so. The per-run overwrite above is a direct loss for the default accumulative mode; these are different claims.

### 2. Explicit lineage and precedence are absent

**Contract.** The 1.53 [`LineageJobFacet`](https://openlineage.io/docs/spec/facets/job-facets/lineage/) names exact source→target relationships; the event’s `inputs` and `outputs` do not authorize a Cartesian product, and the explicit facet takes precedence over conflicting columnLineage. The [`LineageDatasetFacet`](https://openlineage.io/docs/spec/facets/dataset-facets/lineage/) covers DatasetEvents such as derived views without a natural job. Both appear in the [pinned 1.53 schema](https://github.com/manuschillerdev/datahub/blob/feat/openlineage-conformance-combined/metadata-service/openapi-servlet/src/main/resources/openlineage/schemas/1.53.0/facets/LineageFacet.json).

**Minimal sequence.** A JobEvent reports job `specdemo.task`, `inputs:[raw.customers,raw.orders]`, `outputs:[analytics.customer_summary,analytics.order_summary]`, and `job.facets.lineage` with two `entries`: target `analytics.customer_summary` has only source `raw.customers`; target `analytics.order_summary` has only source `raw.orders`. Each entry/source has `type:"DATASET"`, namespace and name; the facet has `_producer` and `_schemaURL:"https://openlineage.io/spec/facets/1-0-0/LineageFacet.json#/$defs/LineageJobFacet"`. Read the two target Dataset upstreamLineage aspects and any job input/output graph. Expected: exactly the two declared edges, with no cross-links. The source predicts **no explicit dataset-to-dataset edge at all**: JobEvent mapping only visits the top-level input/output arrays, and neither the RunEvent nor JobEvent path reads `job.facets.lineage`. It may still create boundary edges through the job, which are not the declared target relationships. [#19800 JobEvent path](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/converter/OpenLineageToDataHub.java#L2384); [ordinary I/O mapping](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/converter/OpenLineageToDataHub.java#L1478).

For the other attachment, send a DatasetEvent for `analytics.customer_summary` with `dataset.facets.lineage.inputs:[{type:"DATASET",namespace:"postgres://warehouse:5432",name:"raw.customers"}]`, the matching `#/$defs/LineageDatasetFacet` schema URL, and read `upstreamLineage`. #19736+ accepts the event but [`convertDatasetEventToMcps`](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/converter/OpenLineageToDataHub.java#L2462) only maps schema, tags, owners, properties and metrics. No native lineage follows. Master does not accept DatasetEvent at this endpoint, so that exact path is **newly reachable but incomplete**; master also has no explicit JobFacet mapping. A producer relying on the accepted 1.53 explicit facet sees an incomplete graph. Missing _native_ lineage is a mapping-support gap; it becomes a semantic conflict if DataHub claims these facets are supported or uses conflicting implicit lineage as authoritative.

### 3. Repeated facets add old tags and owners

**Contract.** A same-name facet on the same entity [replaces its previous instance entirely](https://openlineage.io/docs/spec/facets/). This applies to the OpenLineage producer’s facet value; unrelated DataHub tags/owners need not be erased.

**Minimal sequence.** Send two events for the same job with `job.facets.tags`, first `{"_producer":"https://example.com/producer","_schemaURL":"https://openlineage.io/spec/facets/1-0-0/TagsJobFacet.json#/$defs/TagsJobFacet","tags":[{"key":"owner","value":"A"}]}`, then the same facet with only `[{"key":"owner","value":"B"}]`. Read the DataJob `globalTags` aspect after each. Expected OpenLineage contribution changes from `owner:A` to `owner:B`; source predicts **both** remain. The converter builds the current tag list but the default PATCH path only calls `addTag`; it never removes the old tag. [job tag conversion](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/converter/OpenLineageToDataHub.java#L608); [patch emission](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/dataset/DatahubJob.java#L480). Use `job.facets.ownership` with owner A then B for the same check: [`addOwner`](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/dataset/DatahubJob.java#L497) similarly does not remove A. Supplying an empty tag or owner array makes the converter emit no replacement operation, leaving all old contributions.

#18175 first adds the **job** tag/owner projection on this stack; [its emission path](https://github.com/datahub-project/datahub/blob/e7cad09fc6a6edfe9dd06a8fb3b2ce28ae8cef52/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/dataset/DatahubJob.java#L155) already uses these add-only helpers. #19734 adds dataset tag/owner projections that reuse the same helpers; [#19800 dataset call site](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/dataset/DatahubJob.java#L538). Master had patch-style lineage and some flow tags, but did **not** have these specific job/dataset mappings. This is a semantic bug in a newly advertised mapping, even though additive DataHub PATCH is reasonable for unrelated source contributions.

### 4. `_deleted` facet tombstones are not applied

**Contract.** The 1.53 [core JobFacet and DatasetFacet definitions](https://github.com/manuschillerdev/datahub/blob/feat/openlineage-conformance-combined/metadata-service/openapi-servlet/src/main/resources/openlineage/schemas/1.53.0/OpenLineage.json) allow `_deleted:true` to delete a facet; deletion of a facet is distinct from deletion of the Job/Dataset entity.

**Minimal sequence.** Send a DatasetEvent (on #19736+) for `demo.a` with `dataset.facets.schema` containing `fields:[{"name":"id","type":"int"}]` and standard facet headers. Confirm `schemaMetadata.fields` contains `id`. Send a second DatasetEvent for the same dataset with `dataset.facets.schema:{"_producer":"https://example.com/producer","_schemaURL":"https://openlineage.io/spec/facets/1-2-0/SchemaDatasetFacet.json#/$defs/SchemaDatasetFacet","_deleted":true}`. Read `schemaMetadata` again. Expected: this source’s schema contribution is removed or a clearly documented unsupported-deletion error is returned. Source predicts **no schema removal if the event is accepted**: the typed schema has no `fields`, [`getSchemaMetadata` returns null](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/converter/OpenLineageToDataHub.java#L2503), and [`datasetOnlyMcps`](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/dataset/DatahubJob.java#L122) emits no schema DELETE. If deserialization rejects the valid tombstone instead, that is a separate unsupported-input result to record. The same gap affects a supported facet on a RunEvent, though some full-aspect writes can accidentally clear fields without correctly applying facet-scoped deletion.

Master had no DatasetEvent dispatch; the RunEvent case and absence of a tombstone branch are inherited. #19736 adds DatasetEvent dispatch without the tombstone semantics. The fix should be explicit about DataHub contribution ownership, so deleting one producer’s facet does not remove an unrelated connector’s metadata.

### 5. Omitted facets can disappear

**Contract.** A newly emitted named facet replaces that facet; omission is not deletion. [Facet semantics](https://openlineage.io/docs/spec/facets/) and [core `_deleted` distinction](https://github.com/manuschillerdev/datahub/blob/feat/openlineage-conformance-combined/metadata-service/openapi-servlet/src/main/resources/openlineage/schemas/1.53.0/OpenLineage.json).

**Minimal sequence.** Send a `START` RunEvent with `job.facets.documentation.description:"First description"` and a `run.facets.nominalTime` window. Send `COMPLETE` for the same run/job with empty `job.facets:{}` and `run.facets:{}`. Read the DataJob `dataJobInfo.description` and run `dataProcessInstanceProperties.customProperties`. Expected: documentation and nominal window remain, because neither facet was replaced or deleted. Source predicts `dataJobInfo.description` absent and nominal custom-property keys absent: each event creates fresh `DataJobInfo` and `DataProcessInstanceProperties` objects and unconditionally UPSERTs them, with only current-event facet values. [jobInfo from current event](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/converter/OpenLineageToDataHub.java#L1103); [run properties from current event](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/converter/OpenLineageToDataHub.java#L1376); [unconditional UPSERTs](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/dataset/DatahubJob.java#L181). Master already had whole-aspect writes, though #18175 changes where job documentation is projected. This is a concrete stateful mismatch, not simply missing facet support.

Also check `created` on these aspects in the same sequence: it is built from every incoming `eventTime`, so its latest value becomes the COMPLETE time rather than the original START/creation time. This is a DataHub timestamp-mapping concern rather than an independent OpenLineage protocol rule. [Run property construction](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/converter/OpenLineageToDataHub.java#L1376).

### 6. `int64` from a pinned spec example remains `NullType`

The upstream 1.53 [SchemaDatasetFacet fixture](https://github.com/OpenLineage/OpenLineage/blob/8ad5c14c63fbab63fedd8ff42f9a208d86ad07fe/spec/tests/SchemaDatasetFacet/1.json) contains four `int64` fields; the [pinned schema facet](https://github.com/manuschillerdev/datahub/blob/feat/openlineage-conformance-combined/metadata-service/openapi-servlet/src/main/resources/openlineage/schemas/1.53.0/facets/SchemaDatasetFacet.json) permits free-form type strings. Submit that fixture as a DatasetEvent using the existing generic [OL-039 wrapper](openlineage-evidence/2026-09-18-live/fixtures/OL-039/request.json) on #19736+, then read `schemaMetadata.fields` for `user_id`, `counterparty_id`, `amount`, and `custom_properties.value._1`. Expected DataHub numeric native types and canonical integer field-path tokens. Source predicts `NullType` with `[type=int64]` in paths because [#19800’s normalizer](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/converter/OpenLineageToDataHub.java#L1678) handles `long` and `bigint` but not `int64`, then [falls through to `NullType`](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/converter/OpenLineageToDataHub.java#L1754). [Master’s old switch](https://github.com/datahub-project/datahub/blob/597a64dbd0b227b5e6dd0ad4d083a2d205e1fec1/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/converter/OpenLineageToDataHub.java#L1461) also lacks `int64`.

An older **local** runtime capture confirms the four stored `NullType` values and native API readback: [analysis](openlineage-spec-verification-2026-09-18.md#schemas-and-field-identity), [stored row](openlineage-evidence/2026-09-18-live/fixtures/OL-039/storage.json), and [API response](openlineage-evidence/2026-09-18-live/fixtures/OL-039/api.json). The PR-head prediction is source-based, not a claimed remote execution. Because OpenLineage leaves field types free-form, its spec does not mandate DataHub’s exact type enum; this is a clear mapping-quality defect against a first-party spec fixture and DataHub’s native type meaning.

## Standard 1.53 facet coverage at #19800

This inventory groups the [45-file bundled manifest](https://github.com/manuschillerdev/datahub/blob/feat/openlineage-conformance-combined/metadata-service/openapi-servlet/src/main/resources/openlineage/schemas/1.53.0/manifest.json) (one core schema and 44 facet schema files) against the [#19800 converter](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/converter/OpenLineageToDataHub.java), its [DatahubJob writer](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/dataset/DatahubJob.java), and the PR’s own [real-producer facet inventory](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/test/resources/compatibility/README.md#L28). It is a grouped summary, not a row-by-row assessment of all 44 facet schemas or every event placement. `Mapped` means at least one native aspect/edge, often only part of the facet. `Retained` means a selected scalar or value in DataHub custom properties; it does not imply facet-roundtrip preservation. `Used` means it influences identity or routing. `No projection found` means no reachable mapping/retention branch was found in the inspected converter path, not a proved receiver-wide loss. A standard facet need not have a native DataHub aspect to satisfy the OpenLineage wire protocol. The authors should state support explicitly and avoid treating successful acceptance as preservation.

The manifest’s broad support surface, the corpus’s narrower observed facets, and native DataHub mapping are three different counts.

## Interpretation and evidence boundary

The **direct spec-semantic discrepancies** are partial-event accumulation, same-name facet replacement, facet-scoped `_deleted`, and explicit-lineage precedence _if the endpoint claims/accepts that standard facet as supported_. The **native mapping defects** are `int64` and omitted-facet whole-aspect clobbering. The **coverage limits** are the remaining standard/custom facets in the inventory, which need a declared policy rather than an unsupported claim of universal native mapping. The job graph’s cross-window union is a representation/policy question; it does not by itself prove that a historical job-level graph is invalid.
