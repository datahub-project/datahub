# OpenLineage 1.53.0 contract inventory

This inventory is the contract checklist for the [full DataHub gap comparison](openlineage-gap-comparison-2026-09-28.md). Its [machine-readable companion](openlineage-153-contract-inventory-2026-09-30.json) records every bundled schema definition and per-target verdict slot. **It is not a completed receiver-conformance report:** the target verdicts remain `unverified` until matching revision behavior is traced through conversion, persistence, and readback. A valid JSON schema payload alone establishes only wire shape.

**Pin:** OpenLineage commit [`8ad5c14c63fb`](https://github.com/OpenLineage/OpenLineage/tree/8ad5c14c63fbab63fedd8ff42f9a208d86ad07fe); bundled [manifest](https://github.com/manuschillerdev/datahub/blob/feat/openlineage-conformance-combined/metadata-service/openapi-servlet/src/main/resources/openlineage/schemas/1.53.0/manifest.json). All 45 bundled JSON files match their pinned upstream bytes. The bundle contains one [core schema](https://github.com/OpenLineage/OpenLineage/blob/8ad5c14c63fbab63fedd8ff42f9a208d86ad07fe/spec/OpenLineage.json) and 44 facet files. Of those facet files, **38 are under `spec/facets/` and six are integration registry schemas** (GCP Composer ×2, GCP Dataproc, GCP Lineage, Iceberg scan and commit). Calling all 44 “core standard facets” would be incorrect. The 44 files expose **40 official facet definitions and six bundled registry definitions** (46 attachable definitions total), plus helper shapes for 92 definitions overall. Facet keys and attachment points below were checked against each pinned schema's top-level property and `allOf` base.

## Three event kinds

| Event          | Attachment and required core fields                                                      | Contract question                                                                |
| -------------- | ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `RunEvent`     | Base headers, `run`, `job`; optional `inputs`, `outputs`, `eventType` in the JSON schema | Accept a valid runtime event and preserve its distinct run, job, state, and I/O. |
| `JobEvent`     | Base headers and `job`; optional `inputs`, `outputs`; `run` forbidden                    | Accept design metadata and declared I/O without inventing a run.                 |
| `DatasetEvent` | Base headers and `dataset`; `job` and `run` forbidden                                    | Accept design metadata and update only the identified dataset.                   |

The base headers are `eventTime`, `producer`, and `schemaURL`. The core schema defines the six `eventType` values but does **not** mark `eventType` required on `RunEvent`; the [run-cycle prose](https://github.com/OpenLineage/OpenLineage/blob/8ad5c14c63fbab63fedd8ff42f9a208d86ad07fe/website/docs/spec/run-cycle.md) treats a state update as having a state. Keep wire-schema acceptance and semantic behavior separate. The [object model](https://github.com/OpenLineage/OpenLineage/blob/8ad5c14c63fbab63fedd8ff42f9a208d86ad07fe/website/docs/spec/object-model.md) says JobEvent and DatasetEvent are design-time and have no run.

## Six run states

| State      | Pinned meaning                                                                                                     | Probe                                                               |
| ---------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------- |
| `START`    | beginning of a job run                                                                                             | Send a valid `START` RunEvent and read the resulting run status.    |
| `RUNNING`  | additional information during the run                                                                              | Send a valid `RUNNING` RunEvent and read the resulting run status.  |
| `COMPLETE` | successful conclusion; terminal in run-cycle prose                                                                 | Send a valid `COMPLETE` RunEvent and read the resulting run status. |
| `ABORT`    | abnormally stopped; terminal in run-cycle prose                                                                    | Send a valid `ABORT` RunEvent and read the resulting run status.    |
| `FAIL`     | failed; terminal in run-cycle prose                                                                                | Send a valid `FAIL` RunEvent and read the resulting run status.     |
| `OTHER`    | additional metadata outside standard run cycle; run-cycle prose permits it before START and before terminal states | Send a valid `OTHER` RunEvent and read the resulting run status.    |

The [run-cycle prose](https://github.com/OpenLineage/OpenLineage/blob/8ad5c14c63fbab63fedd8ff42f9a208d86ad07fe/website/docs/spec/run-cycle.md) calls `COMPLETE`, `ABORT`, and `FAIL` terminal and places `OTHER` before terminal states, even before `START`. The [core schema](https://github.com/OpenLineage/OpenLineage/blob/8ad5c14c63fbab63fedd8ff42f9a208d86ad07fe/spec/OpenLineage.json) describes `OTHER` as usable after completion. This is an upstream ambiguity; the report must record DataHub’s actual policy without claiming one unambiguous normative answer.

The core RunFacet has no `_deleted` property. A custom facet with no native DataHub projection is a support-policy choice; silently losing accepted values should still be reported accurately.
