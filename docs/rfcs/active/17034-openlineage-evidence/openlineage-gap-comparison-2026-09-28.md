## Source code can break GraphQL job reads

**Problem:** A valid sourceCode job facet is successfully mapped and persisted as dataTransformLogic with native language UNKNOWN, but DataHub GraphQL only defines SQL. Its enum conversion throws while loading the DataJob. The producer does not have to submit malformed metadata to trigger this.

**Trigger:** Any accepted sourceCode job facet mapped by ours or #19257; bash is a concrete example. SQL-plus-sourceCode also fails because a single UNKNOWN transform is enough.

**Effect on users:** Affected task/job Properties and Lineage pages can show loading errors even though ingestion and native aspect retrieval succeed. This makes source-code-emitting jobs difficult to inspect. Pipeline and run views are separate: saved captures did not show every view or the entire UI failing.

**Expected result:** Ingestion should preserve source text and a subsequent job/task read should return an entity with usable metadata. A valid native UNKNOWN transform should be representable by the read API or handled without aborting the entity read.

### How to reproduce

Method: `manual_http_reproduction_not_executed`.

Prerequisites:

- Use an isolated DataHub instance and an actor allowed to ingest and read metadata. These are reproducible manual requests, not requests executed during this source audit.
- Use the exact target revision from the snapshot, default OpenLineage identity settings (no orchestrator/pipeline override), fresh gap-demo identifiers and native aspect/API readback after ingestion settles.
- Set GMS to the GMS URL and FRONTEND to the frontend URL; bearer-token authentication may be added to curl. POST OpenLineage JSON to $GMS/openapi/openlineage/api/v1/lineage. GraphQL is POST $FRONTEND/api/graphql.
- The recognized Spark producer in these payloads avoids the legacy unknown-producer failure. With defaults, ours uses unknown orchestrator, legacy targets use spark. Draft #19257 can differ in fallback identity: use returned/persisted job URN rather than guessing it.

Inputs (complete request bodies):

- [sourcecode-graphql.json](openlineage-gap-comparison-2026-09-28-reproductions/sourcecode-graphql.json)
- [sourcecode-run.json](openlineage-gap-comparison-2026-09-28-reproductions/sourcecode-run.json)

Steps:

1. Save sourcecode-run.json linked above and POST it to /openapi/openlineage/api/v1/lineage. Record status/body; 2xx alone is insufficient.
2. Read dataTransformLogic for urn:li:dataJob:(urn:li:dataFlow:(unknown,gapdemo,gap-demo),gapdemo.source) on ours. Also read dataJobInfo. Confirm the stored transform language is UNKNOWN and source value is printf hello.
3. POST sourcecode-graphql.json linked above to $GMS/api/graphql (the GMS GraphQL endpoint used by the graph client). For #19257 use the actual persisted job URN. For legacy/master default URN is urn:li:dataJob:(urn:li:dataFlow:(spark,gapdemo,gap-demo),gapdemo.source).
4. Open the same task Properties/Lineage in the UI and record the actual error state; do not extrapolate to pipeline/run views.

Checks:

- Native REST aspect read succeeds with queryStatement.language=UNKNOWN on ours/#19257.
- GraphQL HTTP status may still be 200; inspect errors and data.dataJob. Expected failure is No enum constant com.linkedin.datahub.graphql.generated.QueryLanguage.UNKNOWN and dataJob:null.
- Master/other PRs should not emit this sourceCode native transform; that avoids this trigger but loses source-code metadata. It is unsupported, not a fix to the GraphQL mapper.

Reproduction boundary: No current runtime rerun was performed. The mapper runs eagerly for fetched DataJob aspects, so omitting the transform field from a query is not a reliable workaround. Native API access remains available.

## Dataset rename entity/history migration

**Problem:** A RENAME facet on the new dataset can record a rename operation, but it is not a command that moves the old DataHub entity, properties, lineage edges, assertions, profile history, or operation history. The old and new namespace/name map to separate dataset URNs. Supporting previousIdentifier retention is different from linking or migrating those entities.

**Trigger:** A source table is renamed after metadata/history has already been ingested under its old name; the producer reports the new identifier and previousIdentifier but does not separately backfill/migrate the receiver.

**Effect on users:** Search and lineage can expose an old dataset and a new dataset. Earlier runs, documentation, profiles, assertions, and lineage remain under the old dataset; the new dataset does not automatically inherit them. Users inspecting only the new dataset can believe history/lineage has vanished, and downstream edges may still point at the old name. On the stack, the prior identifier is not retained in native ALTER operation details, making manual reconstruction harder.

**Expected result:** If product users expect continuous history across rename, the receiver needs a native relation/redirect or deliberate migration. The lifecycle facet documents the previous name; it does not specify deleting or moving receiver entities/history, so missing migration is a capability gap rather than a proven conformance bug.

Method: `documented_live_sequence_not_executed`.

Reproduction boundary: This exact live rename sequence was not executed. Current checked-in conformance tests assert operation retention for RunEvent and DatasetEvent; they do not assert migration. ## Legacy parent job edge uses the child job name

**Problem:** The legacy processParentJob builds the parent flow from parent.job but supplies the reporting child job name as the parent DataJob identifier. For two jobs in the same flow, the resulting upstream edge points back to the child itself.

**Trigger:** A COMPLETE RunEvent for gapdemo.child in namespace gap-demo declares parent.job.name=gapdemo.parent in that namespace. Both job names share the gapdemo flow prefix. The supplied Spark producer is recognized by legacy heads, so an unknown-producer failure does not hide this defect.

**Effect on users:** A catalog user following the child task’s upstream job dependency reaches the same child, rather than the actual parent task. The real parent is missing from that edge; lineage navigation and impact analysis can include a spurious self-cycle. The parent job may also have no metadata until it reports its own event. This user effect is predicted from the stored-edge mapping, not a newly captured browser result.

**Expected result:** A legacy job-edge mapping should point to urn:li:dataJob:(urn:li:dataFlow:(spark,gapdemo,gap-demo),gapdemo.parent). The child must not be its own parent. Ours and #19257 instead represent the immediate parent run by parentInstance=urn:li:dataProcessInstance:88888888-8888-4888-8888-888888888888.

### How to reproduce

Method: `source-confirmed HTTP/readback experiment; not executed at these heads`.

Prerequisites:

- A matching disposable GMS build at the selected pinned head, default orchestrator/cluster identity configuration, and permission to ingest/read the example jobs.
- Use a fresh gap-demo namespace or remove prior example metadata. Wait for async persistence before reading the edge.

Inputs (complete request bodies):

- [legacy-parent-identity.json](openlineage-gap-comparison-2026-09-28-reproductions/legacy-parent-identity.json)

Steps:

1. POST the complete legacy-parent-identity.json input using the common OpenLineage curl command above.
2. On master or a legacy PR, GET the child native dataJobInputOutput:

   ```bash
   curl --globoff -fsS -H "Authorization: Bearer $TOKEN" "$GMS/openapi/v3/entity/dataJob/urn:li:dataJob:(urn:li:dataFlow:(spark,gapdemo,gap-demo),gapdemo.child)?aspects=dataJobInputOutput"
   ```

3. Inspect .dataJobInputOutput.value.inputDatajobEdges[].destinationUrn. Compare its final job identifier with parent.job.name in the input.
4. Open the child task lineage view and follow that edge; record whether the UI shows or filters the self-edge. Native readback is the decisive check even if the UI hides cycles.
5. On ours/#19257, read the reporting run urn:li:dataProcessInstance:77777777-7777-4777-8777-777777777777 and its dataProcessInstanceRelationships.parentInstance instead; inspect the actual job URN rather than assuming the legacy spark identity.

Checks:

- Expected parent edge destination ends in ,gapdemo.parent); legacy source predicts the actual destination ends in ,gapdemo.child), equal to the reporting child URN.
- A missing parent job aspect is not by itself the identity bug; the wrong edge destination is.
- Ours/#19257 should identify parentInstance as urn:li:dataProcessInstance:88888888-8888-4888-8888-888888888888. Absence of a legacy DataJob edge is not failure of that native run relation.

Reproduction boundary: All 32 legacy source heads were inspected for this construction, including #14169’s older child job.getName form. Their runtime and browser behavior was not executed. Same-prefix names make this a self-edge; different parent/child flow prefixes instead produce a hybrid, incorrectly named parent job. This is separate from whether forwarded parent facets should materialize parent metadata.

### Result and verification

Evidence level: `source_confirmed`.

**Observed:** The parent builder at master and every legacy PR head takes parent namespace/name for the flow, then takes the child job identifier. Ours and the draft have the separate native parent run mapping.

**Predicted by the current source:** Posting this exact input on a legacy head stores a child-to-itself job dependency. Ours/#19257 use the supplied parent run UUID and do not execute this buggy legacy edge builder on their modular REST path.
