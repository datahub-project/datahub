# OpenLineage 1.53 facet comparison across pinned DataHub targets

Source audit dated 2026-10-01. **This is a facet-only source comparison, not a completed conformance test.** The inventory has 40 official facet definitions from 38 OpenLineage facet schema files plus six bundled GCP/Iceberg extension definitions; missing the latter is a product compatibility limitation, not automatically a 1.53 specification violation.

Specification pin: [`8ad5c14c63fbab63fedd8ff42f9a208d86ad07fe`](https://github.com/OpenLineage/OpenLineage/tree/8ad5c14c63fbab63fedd8ff42f9a208d86ad07fe/spec). DataHub target revisions and source digests are in the [machine matrix](openlineage-153-facet-target-audit-2026-10-01.json).

## Reading the matrix

- `M` = selected native or DataHub property mapping is visible in source. It can lose named fields or have event-specific limits.
- `R` = no native mapping, but the SDK-serialized named facet or input/output observation is retained as JSON in DataHub custom properties in source. Exact original-field fidelity is unverified.
- `I` = accepted event type reaches the converter, but no mapping or general raw retention is visible in the selected source.
- `X` = that event type is rejected before facet mapping. Before #19736 only RunEvent is handled.
- `M/R` = selected native mapping plus SDK-serialized named JSON retention in source; original-field fidelity is unverified.

Every cell is a **source prediction**. It says nothing by itself about successful persistence, read API exposure, or complete field fidelity. The JSON records each canonical attachment separately and labels readback as unverified.

## Catalog and attachment corrections

The initial inventory draft inferred camel case keys for four bundled GCP facets. Their pinned schemas and the receiver catalog use `gcp_composer_job`, `gcp_composer_run`, `gcp_dataproc`, and `gcp_lineage` ([catalog](https://github.com/manuschillerdev/datahub/blob/docs/rfc-openlineage-spec-compliance/docs/rfcs/active/17034-openlineage-evidence/sources/ours-2026-10-01/metadata-service/openapi-servlet/src/main/java/io/datahubproject/openapi/openlineage/validation/OpenLineageSchemaCatalog.java.txt#L125)). The initial draft also listed `DataQualityAssertionsDatasetFacet` at dataset placements, but the pinned facet definition references `InputDatasetFacet`; the receiver catalog registers it only under `inputs[].inputFacets` ([catalog](https://github.com/manuschillerdev/datahub/blob/docs/rfc-openlineage-spec-compliance/docs/rfcs/active/17034-openlineage-evidence/sources/ours-2026-10-01/metadata-service/openapi-servlet/src/main/java/io/datahubproject/openapi/openlineage/validation/OpenLineageSchemaCatalog.java.txt#L181)). The linked inventory JSON and Markdown have been corrected.

## User-visible gaps that remain in the six-PR stack

The 17 official definitions initially marked unprojected at #19800 were rechecked against its converter, typed facet calls, and the `processRunFacetEntry` fallback. One was a false negative: `ErrorMessageRunFacet` maps three fields from #18175 onward. The other 16 have no dedicated mapping or general raw retention in the inspected path. In particular, the `getDataQualityMetrics()` call is for `dataset.facets`, while `getTags()` calls are for job and dataset facets; neither proves mapping for input metrics or run tags. See `rechecked_19800_none_candidates` in the [machine matrix](openlineage-153-facet-target-audit-2026-10-01.json), the [error mapping](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/converter/OpenLineageToDataHub.java#L1386), [typed facet readers](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/converter/OpenLineageToDataHub.java#L2056), and [custom run facet switch](https://github.com/datahub-project/datahub/blob/83f0e634b9243dda2129fa7da8e009c0765700a2/metadata-integration/java/openlineage-converter/src/main/java/io/datahubproject/openlineage/converter/OpenLineageToDataHub.java#L877).

- Facets with `I` in #19800 carry no general retained JSON. Users cannot retrieve the facet from a DataHub entity after ingestion through this path. This includes official subset predicates, execution parameters, run tests, and explicit LineageFacet declarations; GCP/Iceberg reports have the same limitation as bundled vendor extensions. For an individual facet, the server may reject a malformed payload earlier; `I` assumes a valid payload and a recognized producer.
- `M` is often partial: DatasetEvent lifecycle has no operation; JobEvent output statistics have no run operation; ErrorMessageRunFacet stack traces are capped at 4096 characters; source code location retains only selected link details; dataset metrics project only selected profile fields; tag source/structured values and documentation content type are not preserved as native values.
- Neither #19740 batch transport nor #19800 corpus assertions adds facet persistence. A converter golden cannot prove facet replacement, `_deleted`, concurrent ownership, or readback.
