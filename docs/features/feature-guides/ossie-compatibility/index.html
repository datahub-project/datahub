DataHub Entity Model Compatibility with Apache Ossie (OSI)

TL;DR: If you already have an Apache Ossie (OSI) semantic model, almost all of it has a place in DataHub: names, descriptions, expressions, joins, keys, time dimensions, and AI context. DataHub does not read or write Ossie YAML yet. Today you load an Ossie model with the Python SDK, and a handful of fields need a workaround or are dropped. Those are listed in Limitations.

Who this is for: data engineers who author or maintain Ossie semantic models and want to catalog them in DataHub, or who are deciding whether DataHub metadata can be exported to an Ossie-compatible tool.

Spec version: Ossie 0.2.0.dev0. For how Metrics and Semantic Models work in DataHub generally, see Metrics & Semantic Models.

Background​

Apache Ossie (incubating), also written OSI (Open Semantic Interchange), is an open standard for exchanging semantic-layer metadata (semantic models, datasets, fields, relationships, and metrics) between tools. DataHub is a launch partner and designed its Metric and Semantic Model entities to line up with the Ossie shape.

Current support at a glance​

CapabilityStatus
Represent Ossie concepts as DataHub entities✅ Most fields map directly (see the reference)
Load an Ossie model with the Python SDK✅ You write the mapping (see the example)
Import an Ossie YAML file directly (recipe or CLI)❌ Not implemented
Export DataHub metrics and models as Ossie YAML❌ Not implemented
Lossless round trip (Ossie → DataHub → Ossie)❌ Some fields are dropped (see gaps)

Concept Mapping​

The biggest difference is structural, not field by field:

  • Ossie is one nested document. A semantic model contains its datasets, each dataset contains its fields, and relationships and metrics sit alongside them.
  • DataHub splits that document into separate entities linked by references. Each dataset, field, and metric gets its own URN, page, owners, tags, glossary terms, search results, and lineage.
Ossie ConceptDataHub ConceptNotes
Semantic model (document)Semantic Model
datasets[]DatasetSubtype Semantic Model Dataset (a logical dataset). semanticModelProperties.semanticModel points at the model
datasets[].fields[]Schema FieldA column in the logical dataset's schemaMetadata. Its role and expression live on the schema field entity
relationships[]Part of the Semantic ModelStored as records in semanticModelInfo.relationships, not as separate entities
metrics[]MetricmetricInfo.semanticModel points at the model
datasets[].sourceDatasetThe physical table your warehouse connector already ingested, linked by upstream lineage from the logical dataset

Example URNs for the model used later in this guide:

urn:li:semanticModel:(urn:li:dataPlatform:snowflake,analytics,orders_model)
urn:li:dataset:(urn:li:dataPlatform:snowflake,analytics.orders_model.orders_ds,PROD)
urn:li:schemaField:(urn:li:dataset:(urn:li:dataPlatform:snowflake,analytics.orders_model.orders_ds,PROD),amount)
urn:li:metric:(urn:li:dataPlatform:snowflake,analytics,total_revenue)

Two consequences matter in practice:

  1. Lineage runs through the logical datasets. The chain is Metric → Logical dataset → Physical table. The semantic model groups its members but is not a step in that chain.
  2. The URNs you choose matter. An Ossie dataset is identified by its name within one document. In DataHub it needs a globally unique URN, so pick a stable naming scheme such as <schema>.<model>.<dataset>. Metric URNs carry no environment (PROD, DEV), so the same metric in two environments is one entity.

Loading an Ossie model into DataHub today​

There is no Ossie importer yet, but the Python SDK builders (SemanticModel, SemanticModelDataset, Metric) follow the same structure, so a loader is a direct translation. Here is a small Ossie model:

version: "0.2.0.dev0"
name: orders_model
description: A semantic model over the raw orders and customers tables.
ai_context:
  instructions: Use for revenue and customer analytics.
  synonyms: [orders model]
datasets:
  - name: ORDERS
    source: analytics.raw.orders
    primary_key: [order_id]
    fields:
      - name: order_id
        expression: { dialects: [{ dialect: ANSI_SQL, expression: order_id }] }
      - name: customer_id
        expression:
          { dialects: [{ dialect: ANSI_SQL, expression: customer_id }] }
      - name: order_ts
        expression: { dialects: [{ dialect: ANSI_SQL, expression: order_ts }] }
        dimension: { is_time: true }
      - name: amount
        expression: { dialects: [{ dialect: SNOWFLAKE, expression: amount }] }
        ai_context: { synonyms: [revenue] }
  - name: CUSTOMERS
    source: analytics.raw.customers
    primary_key: [customer_id]
    fields:
      - name: customer_id
        expression:
          { dialects: [{ dialect: ANSI_SQL, expression: customer_id }] }
      - name: customer_name
        expression:
          { dialects: [{ dialect: ANSI_SQL, expression: customer_name }] }
relationships:
  - name: orders_to_customers
    from: ORDERS # the "many" side
    to: CUSTOMERS # the "one" side
    from_columns: [customer_id]
    to_columns: [customer_id]
metrics:
  - name: total_revenue
    description: Sum of all order amounts.
    expression:
      { dialects: [{ dialect: SNOWFLAKE, expression: SUM(ORDERS.amount) }] }
    ai_context: { synonyms: [revenue] }

The same model built with the SDK. Comments mark the Ossie field each argument comes from:

from pathlib import Path

from datahub.emitter.mce_builder import make_dataset_urn
from datahub.metadata.schema_classes import (
    DialectClass,
    ERModelRelationshipCardinalityClass,
    SemanticFieldTypeClass,
)
from datahub.metadata.urns import SemanticModelUrn
from datahub.sdk import (
    AiContextInput,
    DataHubClient,
    DialectExpressionInput,
    Metric,
    SemanticFieldInput,
    SemanticModel,
    SemanticModelDataset,
    SemanticModelRelationshipInput,
)

platform = "snowflake"
model_urn = SemanticModelUrn(platform=platform, path="analytics", id="orders_model")

orders = SemanticModelDataset(
    platform=platform,
    name="analytics.orders_model.orders_ds",  # your URN naming scheme
    semantic_model=model_urn,
    alias="ORDERS",  # datasets[].name, used by relationships
    upstreams=[make_dataset_urn(platform, "analytics.raw.orders")],  # datasets[].source
    schema=[
        SemanticFieldInput(
            field_path="order_id",  # fields[].name
            type="int",  # DataHub needs a type; Ossie datatype is optional
            semantic_type=SemanticFieldTypeClass.DIMENSION,  # not in Ossie, see below
            is_part_of_key=True,  # datasets[].primary_key
        ),
        SemanticFieldInput(
            field_path="customer_id",
            type="int",
            semantic_type=SemanticFieldTypeClass.DIMENSION,
        ),
        SemanticFieldInput(
            field_path="order_ts",
            type="timestamp",
            semantic_type=SemanticFieldTypeClass.DIMENSION,
            is_time_dimension=True,  # fields[].dimension.is_time
        ),
        SemanticFieldInput(
            field_path="amount",
            type="float",
            semantic_type=SemanticFieldTypeClass.MEASURE,
            expression=DialectExpressionInput(  # fields[].expression
                expression="amount", dialect=DialectClass.SNOWFLAKE
            ),
            aggregation_function="SUM",  # not in Ossie
            ai_context=AiContextInput(synonyms=["revenue"]),  # fields[].ai_context
        ),
    ],
)

customers = SemanticModelDataset(
    platform=platform,
    name="analytics.orders_model.customers_ds",
    semantic_model=model_urn,
    alias="CUSTOMERS",
    upstreams=[make_dataset_urn(platform, "analytics.raw.customers")],
    schema=[
        SemanticFieldInput(
            field_path="customer_id",
            type="int",
            semantic_type=SemanticFieldTypeClass.DIMENSION,
            is_part_of_key=True,
        ),
        SemanticFieldInput(
            field_path="customer_name",
            type="varchar",
            semantic_type=SemanticFieldTypeClass.DIMENSION,
        ),
    ],
)

total_revenue = Metric(
    platform=platform,
    path="analytics",
    id="total_revenue",  # metrics[].name
    name="Total Revenue",
    description="Sum of all order amounts.",  # metrics[].description
    semantic_model=str(model_urn),
    expression=DialectExpressionInput(  # metrics[].expression
        expression="SUM(ORDERS.amount)", dialect=DialectClass.SNOWFLAKE
    ),
    upstream_datasets=[orders.urn],  # lineage, not in Ossie
    ai_context=AiContextInput(synonyms=["revenue"]),  # metrics[].ai_context
)

model = SemanticModel(
    platform=platform,
    path="analytics",
    id="orders_model",
    name="orders_model",  # name
    description="A semantic model over the raw orders and customers tables.",
    native_definition=Path("orders_model.ossie.yaml").read_text(),  # keep the original
    datasets=[orders, customers],
    relationships=[
        SemanticModelRelationshipInput(
            name="orders_to_customers",  # relationships[].name
            from_alias="ORDERS",  # relationships[].from
            from_columns=["customer_id"],  # relationships[].from_columns
            to_alias="CUSTOMERS",  # relationships[].to
            to_columns=["customer_id"],  # relationships[].to_columns
            cardinality=ERModelRelationshipCardinalityClass.N_ONE,  # Ossie's from=many, to=one
        )
    ],
    ai_context=AiContextInput(  # ai_context
        synonyms=["orders model"],
        instructions="Use for revenue and customer analytics.",
    ),
)

client = DataHubClient(server="<your-gms-url>", token="<your-token>")
for entity in [model, orders, customers, total_revenue]:
    client.entities.upsert(entity)

Things to decide when you write the loader:

  • Field type and role. DataHub requires a column type and a semantic role (DIMENSION, MEASURE, FILTER, or OTHER) for every field. Ossie has neither as a required field. Map Ossie datatype to a native type string when it is present. For the role, a common rule is dimension present → DIMENSION, otherwise MEASURE, adjusted by naming conventions.
  • Cardinality. Ossie defines from as the many side and to as the one side, so every Ossie relationship maps to N_ONE.
  • Keep the original YAML. Store the source file in native_definition. It is shown on the semantic model page and keeps everything DataHub has no field for, such as the spec version, unique_keys, and custom_extensions.
  • Physical sources. upstreams expects the URN of a physical table that your warehouse connector has already ingested. Build it from Ossie source with the same platform, platform instance, and environment, or lineage will point at a table that does not exist.

The SDK also writes things Ossie has no field for, including the dataset subtype, membership pointers, and metric lineage. For the full aspect list, see the Semantic Models & Metrics SDK guide.

Limitations​

These Ossie fields have no exact DataHub field. Use the workaround column if the information matters to you.

Ossie fieldWhat happens in DataHubWorkaround
Document versionNot storedKept in native_definition if you store the source YAML
Dataset.source when it is a query, not a tableLineage needs a table URN, so a query has nowhere to goPoint upstreams at the tables the query reads. Keep the query in native_definition
Dataset.unique_keysNot storedUse a structured property, or rely on native_definition
Dataset.ai_contextLogical datasets do not have an AI context aspectPut the synonyms and instructions on the model's or the fields' AI context
Dataset.primary_keyStored per column (is_part_of_key), not as an ordered listColumn order of a composite key is not preserved. Keep it in native_definition if order matters
Field.labelStored on a deprecated field that the UI does not showPut the display label in the field description
Field.datatypeStored as DataHub's own type plus the native type string, not the Ossie enumMap in both directions in your loader
Metric.datatypeNot storedUse a structured property on the metric
ai_context as a plain stringDataHub only stores the object formPut the string in instructions
Extra keys in an ai_context objectOnly one free-form string, customInstructionsSerialize the extra keys into customInstructions (for example as JSON)
A dialect DataHub has no named value forStored as OTHER, so the dialect name is lostKeep the original in native_definition. See Expressions and dialects
custom_extensions[] (everywhere)Not storedUse structured properties, which are typed, searchable, and shown in the UI

Going the other way: DataHub → Ossie​

DataHub allows a few things that Ossie rejects. If you plan to export later, enforce these in your loader:

  • Every metric needs an expression. It is optional in DataHub and required in Ossie.
  • Every relationship needs a name. It is optional in DataHub and required in Ossie.
  • Ossie has no many-to-many join. N_ONE maps directly, ONE_N maps by swapping from and to, and ONE_ONE fits either way. N_N has no Ossie representation.

DataHub also stores information that Ossie has no field for:

DataHub fieldWhat it holds
semanticFieldAnnotation.typeField role: DIMENSION, MEASURE, FILTER, or OTHER
semanticFieldAnnotation.aggregationFunctionAggregation for MEASURE fields, such as SUM, COUNT_DISTINCT, or AVG
semanticModelRelationship.cardinalityJoin cardinality: ONE_ONE, ONE_N, N_ONE, or N_N
semanticModelInfo.nativeDefinitionThe original source definition, verbatim (Snowflake DDL, dbt YAML, Ossie YAML)
metricRelationships.parentMetricParent in a metric hierarchy
metricRelationships.derivedFromMetrics this metric is computed from
metricRelationships.relatedMetricsRelated metrics, not lineage
metricUpstreams.datasetUpstreams / fieldUpstreamsDataset- and column-level lineage for the metric
Owners, domains, tags, glossary terms, structured propertiesGovernance metadata on every entity

An exporter could carry these in Ossie custom_extensions (a vendor_name plus a JSON data string). No DataHub code does this today.

Expressions and dialects​

An Ossie expression is { dialects: [{ dialect, expression }] }. DataHub's MetricExpression and DialectExpression use the same shape, and both dialect and expression are required. One expression can carry several dialects, and the SDK accepts a list of DialectExpressionInput.

DataHub supports a subset of the Ossie dialects as named values. The current list is the Dialect enum in Dialect.pdl. Any Ossie dialect without a named value there is stored as OTHER, the fallback, and the original dialect name is lost. Keep the source YAML in native_definition if you need it.

AI context​

DataHub's AiContext record follows the object form of Ossie ai_context. It is an aspect on metrics, semantic models, and schema fields, and is stored inside each relationship. Logical datasets do not have it.

Ossie ai_contextDataHubNotes
instructions✅ AiContext.instructions
synonyms✅ AiContext.synonyms
examples✅ AiContext.examples
Plain-string form❌ —Put the string in instructions
Extra object properties⚠️ AiContext.customInstructionsOne free-form string, not a key-value map
